## Overview

Checks whether patient data would resolve a valid IHI **before** you create the patient. Send the identical body you would send to [Create Patient](/api-reference/endpoint/v1/create-patient) — the precheck runs the same HI Service search that creation performs, but never creates a patient and never returns the IHI number itself.

Every result is codified in `data.outcome` so your integration can branch programmatically — there are no free-text reason strings to parse.

Two orthogonal flags answer the two questions partners ask:

- **`create_would_succeed`** — would an identical create request succeed right now? (`true` for `already_exists`: creation returns the existing patient idempotently; `true` for `no_match`: the patient is created, just without an IHI.)
- **`ihi_check_passed`** — did the live HI Service search resolve a usable IHI (`ihi_status: ACTIVE` + `ihi_record_status: VERIFIED`, the same bar prescribing eligibility uses)? Present only when a search actually completed; absent means the check was not performed.

## Outcomes

| `outcome` | Meaning | `create_would_succeed` | `ihi_check_passed` |
|---|---|---|---|
| `ihi_found` | A live HI Service search matched an IHI. Check `ihi_record_status`: creation is rejected while the record is `PROVISIONAL` or `UNVERIFIED`. | `true` unless record is `PROVISIONAL`/`UNVERIFIED` | `true` only if `ACTIVE` + `VERIFIED` |
| `no_match` | The search ran but no IHI resolved. Creation still succeeds — the patient is created without an IHI. May include `ihi_status` (e.g. `EXPIRED`, `RETIRED`) when the HI Service reported one. | `true` | `false` |
| `insufficient_data` | No search path can run with the supplied fields. `search_paths` lists, per path, the fields that would unlock it. | `false` (no identifier at all) or `true` (Medicare supplied without `medicare_irn`) | absent |
| `already_exists` | A patient with this `partner_patient_id` already exists for the organization (`parchment_patient_id`, stored `has_ihi`). **The live IHI check still runs** with the submitted data and its result is reported (`ihi_check_passed`, `searched_path`, live `ihi_status`/`ihi_record_status`). If no search path can run or the HI Service is unreachable, stored statuses are returned and `ihi_check_passed` is absent. Creation returns this patient idempotently. | `true` | live result, or absent if the check couldn't run |
| `organization_not_ready` | The organization has no HPI-O configured, so no IHI search is possible. Contact Parchment. | `false` | absent |
| `hi_service_error` | The HI Service could not be reached (timeout or outage). Retry later. | `false` | absent |

## Search Paths

Exactly **one** search path is attempted per request, selected in priority order from the identifiers you supply — there is no fallback to a lower-priority identifier:

| Priority | `searched_path` | Requires |
|---|---|---|
| 1 | `ihi_number` | `ihi_number` |
| 2 | `medicare` | `medicare_card_number` + `medicare_irn` |
| 3 | `dva` | `dva_file_number` |
| 4 | `australian-street-address` | `australian_street_address` (all fields) |
| 5 | `international-address` | `international_address` (all fields) |

All paths also require the base demographics: `family_name`, `given_name`, `date_of_birth`, `sex`.

### Validation Error (422 Unprocessable Entity)

Returned for schema failures **and** identifier format failures (Medicare checksum, IHI check digit, future date of birth). All field problems are reported together in a single response:

## Response Fields

### Precheck Response Data

| Field | Type | Description |
|-------|------|-------------|
| `outcome` | string | One of `ihi_found`, `no_match`, `insufficient_data`, `already_exists`, `organization_not_ready`, `hi_service_error` |
| `create_would_succeed` | boolean | Whether an identical create request would currently succeed |
| `ihi_check_passed` | boolean | Present when a live search completed: `true` only for an `ACTIVE` + `VERIFIED` IHI. Absent = check not performed |
| `searched_path` | string | The search path used (present when a live search ran) |
| `ihi_status` | string | `ACTIVE`, `DECEASED`, `RETIRED`, `EXPIRED`, `RESOLVED`, `UNKNOWN` — live result when the search ran; stored value for `already_exists` when it couldn't |
| `ihi_record_status` | string | `VERIFIED`, `UNVERIFIED`, `PROVISIONAL`, `UNKNOWN` — same sourcing as `ihi_status` |
| `has_ihi` | boolean | `already_exists` only: whether the **stored** patient record holds an IHI |
| `parchment_patient_id` | string | `already_exists` only |
| `search_paths` | array | `insufficient_data` only: fields that would unlock each search path |

### Common Response Fields

| Field | Type | Description |
|-------|------|-------------|
| `success` | boolean | Whether the request succeeded |
| `statusCode` | number | HTTP status code |
| `message` | string | Human-readable result message |
| `timestamp` | string | ISO 8601 response timestamp |
| `requestId` | string | Unique request identifier for support |

## Status Codes

| Code | Meaning |
|------|---------|
| 200 | Precheck completed — read `data.outcome` |
| 401 | Authentication failed (invalid token, secret, or scope) |
| 409 | Multiple patients already share this `partner_patient_id` |
| 422 | Validation failed — see `error.validation` |
| 500 | Unexpected server error |

## Notes

- Requires the same `create:patient` scope as Create Patient.
- The IHI number is never returned — create the patient to have Parchment store and manage the IHI.
- A Medicare number without `medicare_irn` reports `insufficient_data`: the search technically runs without the IRN at creation time, but rarely matches.
